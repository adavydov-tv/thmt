# user-activity-dashboard

Сервис собирает активность конкретного человека из **Jira Cloud**, **self-hosted GitLab**,
**Slack** и **Google Docs** за заданный период, складывает всё в единую модель событий
в PostgreSQL и показывает графики и статистику с возможностью провалиться в детали
каждого источника.

Отдельная фича: если в задаче Jira есть ссылка на Google-документ (TSD), сервис
находит её, привязывает документ к задаче и подтягивает историю правок и
комментариев по нему — на странице «Документы» видно связку **задача ↔ документ**.

```
┌────────┐  ┌────────┐  ┌───────┐  ┌────────────┐
│  Jira  │  │ GitLab │  │ Slack │  │ Google Docs│
└───┬────┘  └───┬────┘  └───┬───┘  └─────┬──────┘
    │           │           │            │            ссылки на доки
    └───────────┴─────┬─────┴────────────┘            ─────────────►
                      ▼                                (Jira → GDocs)
              коллекторы (Go)
                      ▼
              единая модель Event
                      ▼
                 PostgreSQL
                      ▼
                  HTTP API
                      ▼
            React + Recharts (SPA)
```

## Быстрый старт

```bash
cp .env.example .env          # заполните токены, см. раздел «Токены доступа»
make db                       # PostgreSQL в docker на :5432
make deps                     # go mod tidy + npm install
make build-front              # сборка SPA в web/dist
make run                      # API + фронтенд на http://localhost:8080
```

Дальше — на `/settings`: проверьте идентификаторы человека, выберите период и
нажмите «Собрать». Прогресс по каждому источнику отображается там же.

Разработка фронтенда с горячей перезагрузкой:

```bash
make run        # терминал 1: бэкенд на :8080
make dev-front  # терминал 2: Vite на :5173, проксирует /api на :8080
```

Разовый сбор из командной строки (удобно для крона):

```bash
make collect PERSON=adavydov FROM=2026-07-01 TO=2026-08-14
```

## Токены доступа

Все секреты живут **только** в переменных окружения — единственное место в коде,
где они читаются, это `internal/config/config.go`. Полный список с комментариями —
в `.env.example`. Ниже — что именно нужно завести в каждой системе.

### Jira Cloud

| Переменная | Что это |
|---|---|
| `JIRA_BASE_URL` | `https://your-company.atlassian.net` |
| `JIRA_EMAIL` | e-mail владельца токена |
| `JIRA_API_TOKEN` | https://id.atlassian.com/manage-profile/security/api-tokens |

Авторизация — Basic (`email:token` в base64), REST API v3. Сервис использует новый
курсорный `/rest/api/3/search/jql` и автоматически откатывается на устаревший
`/rest/api/3/search`, если инстанс его ещё не поддерживает.

`jira_account_id` человека можно узнать через `GET /rest/api/3/myself` или из URL
его профиля. Он важнее e-mail: Jira Cloud скрывает почту в API, и поиск по
`accountId` заметно точнее.

### GitLab (self-hosted)

| Переменная | Что это |
|---|---|
| `GITLAB_BASE_URL` | `https://gitlab.your-company.com` |
| `GITLAB_TOKEN` | Personal Access Token, scopes `read_api` + `read_repository` |

Токен создаётся в профиле: *Preferences → Access Tokens*. Если у инсталляции
самоподписанный сертификат — `GITLAB_SKIP_TLS_VERIFY=true`.

### Slack

Работают две стратегии, достаточно одной:

1. **User token** `SLACK_USER_TOKEN` (`xoxp-…`) со scope `search:read` — быстрый путь
   через `search.messages`, видит все каналы, где состоит владелец токена.
2. **Bot token** `SLACK_BOT_TOKEN` (`xoxb-…`) со scopes `channels:history`,
   `groups:history`, `channels:read`, `groups:read`, `users:read`, `users:read.email` —
   фолбэк через обход каналов. Бот должен быть приглашён в каналы, иначе они
   пропускаются.

Реакции доступны только во второй стратегии — у `search.messages` их нет в ответе.
Выбранная стратегия и все пропуски пишутся в примечание к прогону и видны в UI.

`slack_user_id` (`U…`) берётся из профиля: *«Copy member ID»*.

### Google Docs / Drive

`GOOGLE_AUTH_MODE` переключает два способа авторизации:

**`service_account`** — для сервиса без интерактивного логина.

1. В GCP создайте сервис-аккаунт, включите **Drive API** и **Drive Activity API**.
2. Скачайте JSON-ключ → `GOOGLE_CREDENTIALS_FILE` (или положите его содержимое
   одной строкой в `GOOGLE_CREDENTIALS_JSON` — удобно для k8s-секретов).
3. Чтобы видеть активность конкретного человека, включите **domain-wide delegation**
   в Google Workspace Admin для scopes ниже и задайте `GOOGLE_IMPERSONATE_SUBJECT`
   с его e-mail. Без impersonation сервис-аккаунт видит только то, что расшарено
   на него самого.

**`oauth`** — ходим от имени вашего аккаунта. Нужны `GOOGLE_OAUTH_CLIENT_ID`,
`GOOGLE_OAUTH_CLIENT_SECRET` и одноразово полученный `GOOGLE_OAUTH_REFRESH_TOKEN`.

Используемые scopes: `drive.activity.readonly`, `drive.readonly`, `drive.metadata.readonly`.

> **Как определяется автор.** Drive Activity API отдаёт актора как `people/<id>` —
> без e-mail и имени. Тот же id лежит в `permissionId` пользователя в Drive, поэтому
> карта `people-id → (e-mail, имя)` собирается из прав доступа документа, его
> ревизий, авторов комментариев и метаданных файла.
>
> Сопоставление идёт по трём признакам, в порядке надёжности:
>
> 1. **e-mail** (`google_email`, затем `email` из карточки человека). Признак
>    работает в обе стороны: если адрес есть и он чужой — это другой человек,
>    и совпадение имени ничего не меняет. Тёзки встречаются чаще, чем хотелось бы.
> 2. **отображаемое имя** (`display_name`) — когда адреса нет вовсе. Для
>    комментариев это основной случай: Drive Comments API сплошь и рядом отдаёт
>    автора без e-mail.
> 3. **флаг `IsCurrentUser` / `me`** — засчитывается, только если учётка API и есть
>    тот самый человек.
>
> Признак, по которому опознан автор, пишется в событие (`meta.matched_by`,
> `meta.actor_matched_by`), а сводка «автор опознан по: email=…, display_name=…» —
> в примечание к прогону.
>
> **Активность, чьего автора опознать не удалось, отбрасывается**, а не
> приписывается человеку. В примечании к прогону перечислены те, чьи действия были
> отброшены как чужие, — по этому списку сразу видно, если в выборку лезет не тот
> человек или если у вашего сотрудника в Drive другое написание имени.

### HRDB (Atlassian Assets)

Список сотрудников подтягивается из HRDB — объектов «Employee» в Atlassian
Assets (JSM Insight). Авторизация — те же `JIRA_EMAIL` / `JIRA_API_TOKEN`.

| Переменная | Что это |
|---|---|
| `HRDB_WORKSPACE_ID` | id workspace Assets: `GET /rest/servicedeskapi/assets/workspace` |
| `HRDB_EMPLOYEE_TYPE_ID` | objectTypeId типа «Employee» в схеме HRDB |
| `HRDB_EMPLOYEE_NAME_ATTR` / `HRDB_EMPLOYEE_EMAIL_ATTR` | id атрибутов; пусто — ищутся по имени («Display Name» / «Work Email») |

На `/settings` появляется блок «Сотрудники из HRDB»: выбираете человека —
и сервис по его e-mail сам находит аккаунты во всех системах
(`POST /api/people/discover`):

- **Jira** — `/rest/api/3/user/search?query=email` → `accountId`;
- **GitLab** — `/api/v4/users?search=email` → `username` (точное совпадение
  адреса приоритетнее единственного результата поиска);
- **Slack** — `users.lookupByEmail` (нужен scope `users:read.email`);
- **Google** — идентификатором служит сам e-mail.

Результат по каждой системе показывается явно («найден / не найден / ошибка»),
неоднозначные совпадения не угадываются — карточку можно поправить руками до
сохранения. Та же кнопка «Найти аккаунты по e-mail» есть и в форме человека.

### Кого собираем

`ACTIVITY_PEOPLE` — JSON-массив (или путь к JSON-файлу) с идентификаторами человека
во всех четырёх системах:

```json
[{
  "key": "adavydov",
  "display_name": "Aleksei Davydov",
  "email": "adavydov@tradingview.com",
  "jira_account_id": "5f1a…",
  "gitlab_username": "adavydov",
  "slack_user_id": "U01ABCDEF",
  "google_email": "adavydov@tradingview.com"
}]
```

Эти значения загружаются в таблицу `people` при старте; дальше их можно править
через UI на `/settings` — правки в БД не затираются, пока вы не поменяете ENV.

## Что считается активностью

| Источник | Типы событий |
|---|---|
| **Jira** | создание задачи, назначение, закрытие, переходы статусов, изменения полей, комментарии, ворклоги (с учётом списанного времени) |
| **GitLab** | коммиты (с числом изменённых строк), push, открытие / merge / закрытие / апрув MR, комментарии ревью, заметки, issues |
| **Slack** | сообщения в каналах, ответы в тредах, реакции |
| **Google Docs** | правки, комментарии, предложения правок, создание документов |

Все события приводятся к одной структуре (`internal/models`): источник, тип, время,
заголовок, ссылка, проект/репозиторий/канал, `ref_id` сущности и `effort` — числовая
мера объёма (секунды для ворклогов, строки для коммитов). Благодаря `ref_id` в UI
можно провалиться из любого события во всю историю по задаче, MR, треду или документу.

Идентификатор события детерминирован (`sha1` от источника, типа и внешнего id),
поэтому повторный сбор того же периода не плодит дублей. Перед записью окно данных
по источнику очищается — исчезнувшее в источнике не залипает в базе.

## API

Базовый префикс `/api`. Общие query-параметры статистики и событий:
`person_key` (обязателен), `from`, `to` (RFC3339, `YYYY-MM-DD` или относительное `-30d`),
`tz`, повторяемые или через запятую `source`, `type`, `project`, полнотекстовое `q`.

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/api/health` | состояние БД и сконфигурированных источников |
| `GET` | `/api/meta` | список источников, подписи типов событий |
| `GET` | `/api/people` | люди |
| `POST` | `/api/people` | создать/обновить человека |
| `GET` | `/api/hrdb/employees` | сотрудники из HRDB (`q` — поиск по имени/e-mail) |
| `POST` | `/api/people/discover` | найти аккаунты по e-mail во всех системах (`{email, key?, display_name?}`) |
| `GET` | `/api/people/{key}/projects` | проекты для фильтров |
| `POST` | `/api/sync` | запустить сбор (`{person_key, from, to, sources?}`) → `202` |
| `GET` | `/api/sync/{id}` | статус прогона с прогрессом по источникам |
| `GET` | `/api/sync` | история прогонов |
| `GET` | `/api/stats/summary` | сводка + сравнение с предыдущим равным периодом |
| `GET` | `/api/stats/timeline` | временной ряд, `granularity=hour\|day\|week\|month` |
| `GET` | `/api/stats/breakdown` | разбивка, `dimension=source\|type\|project` |
| `GET` | `/api/stats/heatmap` | матрица «день недели × час» |
| `GET` | `/api/events` | лента с фильтрами и пагинацией |
| `GET` | `/api/events/{id}` | событие + все связанные по `ref_id` |
| `GET` | `/api/refs/{refID}/events` | вся история по сущности |
| `GET` | `/api/docs` | Google-документы, связанные с задачами Jira |
| `GET` | `/api/purge/preview` | сколько данных попадёт под удаление (ничего не меняет) |
| `POST` | `/api/purge` | удалить собранные данные за период |

Удаление требует явных `person_key`, `from`, `to` и `confirm: true` — «снести всё»
не должно получаться из-за незаполненного фильтра. Опционально сносится история
прогонов за тот же период (`sync_runs`) и обнуляются счётчики правок по документам
(`reset_doc_links`). В UI это блок «Удаление собранных данных» на `/settings`:
сначала показывается разбивка того, что исчезнет, и только потом появляется кнопка
удаления с отдельным подтверждением.

Ошибки — `{"error": "…"}` с соответствующим HTTP-статусом.

## Интерфейс

Фильтр «Период» в шапке работает по календарным периодам: выбираете вид —
день, неделя, месяц, квартал или год — и конкретный период этого вида
(например, «Квартал → Q2 2026»); границы дат проставляются сами. Тот же
селектор есть в панели сбора на `/settings` — так в один клик загружается
целый квартал или год. Вид «Произвольный» оставляет привычные две даты.

| Страница | Что показывает |
|---|---|
| `/` | KPI-плитки с дельтой к прошлому периоду, накопленный график по источникам, распределение по источникам, топ проектов, **матрица активности по дням** (календарь контрибуций, как в GitLab), тепловая карта «день × час», последние события |
| `/source/:source` | детализация одного источника: свои метрики, таймлайн, разбивка по типам, топ репозиториев/каналов, лента с фильтрами |
| `/docs` | TSD-документы и связанные задачи; клик по строке — история правок и комментариев |
| `/events` | лента с фильтрами по источникам, типам, проекту и поиском |
| `/events/:id` | карточка события со всеми полями и `meta` + вся история по сущности |
| `/settings` | люди, запуск сбора, прогресс и история прогонов |

Состояние фильтров живёт в URL — ссылкой на конкретный срез можно поделиться.
У каждого графика есть переключатель «Таблица» — те же данные обычной таблицей.
Есть светлая и тёмная тема (палитра для каждой подобрана отдельно и проверена
на различимость при дальтонизме, а не получена инверсией).

## Эксплуатация

- **Ретраи.** Все внешние вызовы уважают `Retry-After` и `429`, с экспоненциальной
  задержкой (`SYNC_MAX_RETRIES`).
- **Частичный результат.** Если один источник упал, остальные всё равно сохранятся;
  прогон помечается статусом `partial`, а ошибка видна в UI рядом с источником.
- **Порядок сбора.** Jira выполняется первой и синхронно — она поставляет ссылки на
  документы, без которых Google-коллектору нечего обходить. Остальные три идут
  параллельно (`SYNC_CONCURRENCY`).
- **Одновременность.** Два сбора по одному человеку не запускаются: повторный
  запрос вернёт `409` с текущим прогоном.
- **Docker.** `docker compose --profile full up -d` поднимет и БД, и приложение
  (образ собирается из `Dockerfile`, включая фронтенд).
- **Kubernetes.** Helm-чарт в `deploy/helm/activity-dashboard` (по образцу
  incidentbot-go): встроенный Postgres для staging, Secret/ConfigMap-разделение,
  ingress/tvingress, production-предохранители. Как деплоить —
  `deploy/helm/README.md`; CI-конвейер — `.gitlab-ci.yml`.

## Типовые проблемы с доступами

### Slack: `missing_scope`

Скоупы в Slack выдаются приложению при установке — добавить их «на лету» нельзя,
нужно дописать список и переустановить приложение.

1. https://api.slack.com/apps → ваше приложение → **OAuth & Permissions**.
2. В **User Token Scopes** добавьте: `search:read`, `channels:history`,
   `channels:read`, `groups:history`, `groups:read`, `users:read`, `users:read.email`.
3. **Reinstall to Workspace** и скопируйте новый `xoxp-…` в `SLACK_USER_TOKEN`.

Пользовательский токен предпочтительнее ботового: `search:read` в принципе
недоступен ботам, а приватные каналы видны без приглашения приложения в каждый
из них. Если политика воркспейса требует одобрения администратора — установка
повиснет в очереди на approve.

Ботовый токен как запасной вариант требует тех же `*:history` / `*:read`
плюс приглашения бота (`/invite @app`) в каждый интересующий канал.

При ошибке сервис печатает и запрошенные, и фактические скоупы токена — Slack
отдаёт их заголовками `x-accepted-oauth-scopes` и `x-oauth-scopes`, так что
гадать, чего именно не хватает, не придётся.

### Google: `unauthorized_client`

Означает, что сервис-аккаунту не разрешено ходить от имени сотрудника —
domain-wide delegation не настроен.

**Если есть доступ к Google Workspace Admin:**

1. GCP → сервис-аккаунт → *Advanced settings* → включить domain-wide delegation,
   скопировать **числовой Client ID**.
2. Google Admin → *Security* → *Access and data control* → *API controls* →
   *Domain-wide delegation* → *Add new*: этот Client ID и scopes одной строкой:
   ```
   https://www.googleapis.com/auth/drive.activity.readonly,https://www.googleapis.com/auth/drive.readonly,https://www.googleapis.com/auth/drive.metadata.readonly
   ```
3. Убедитесь, что в проекте GCP включены **Google Drive API** и **Drive Activity API**.
4. `GOOGLE_IMPERSONATE_SUBJECT` — реальный e-mail сотрудника в этом домене.

Применяется за несколько минут.

**Если прав администратора нет, вариант «только расшаренные документы».**
Уберите `GOOGLE_IMPERSONATE_SUBJECT` — с пустым значением JWT-запрос перестаёт
быть делегированным и проходит без всяких настроек в Admin. Сервис-аккаунт
работает как обычный пользователь со своим (пустым) Drive и видит ровно то, что
на него расшарили.

```bash
GOOGLE_AUTH_MODE=service_account
GOOGLE_CREDENTIALS_FILE=./secrets/google-service-account.json
GOOGLE_IMPERSONATE_SUBJECT=          # ← пусто
GOOGLE_SCAN_DRIVE=true
GOOGLE_DRIVE_FOLDER_IDS=             # опционально: id папки с TSD
```

Что происходит в этом режиме:

- документы, найденные по ссылкам в задачах Jira, обходятся как обычно — если
  доступ на них есть;
- вместо бессмысленного обхода `items/root` (у сервис-аккаунта свой пустой Drive)
  сервис ищет доступные документы через `files.list` с `sharedWithMe = true`,
  либо внутри папок из `GOOGLE_DRIVE_FOLDER_IDS`, и обходит найденное поштучно;
- если у документа закрыта лента Drive Activity — а читателю её часто не
  показывают — событие всё равно создаётся из метаданных файла
  (`modifiedTime` + `lastModifyingUser`) и помечается `meta.approximate = true`.
  Это огрубление: видна последняя правка, а не каждая.

Чтобы документы стали видны, их надо расшарить на адрес сервис-аккаунта — он
лежит в поле `client_email` внутри JSON-ключа и печатается в лог при старте
сбора. Практичнее всего расшарить одну папку с TSD и указать её id в
`GOOGLE_DRIVE_FOLDER_IDS`. Режим, учётка и число найденных документов видны
в примечании к прогону на странице настроек.

**Все документы, доступные вашему аккаунту — режим `oauth`.** Сервис ходит в
Drive от вашего имени и видит ровно то, что видите вы: «Мой диск», «Доступные
мне» и общие диски. Ни delegation, ни шаринга на сервис-аккаунт не требуется.

```bash
# APIs & Services → Credentials → OAuth client ID → тип «Desktop app»
make google-auth
```

```bash
GOOGLE_AUTH_MODE=oauth
GOOGLE_OAUTH_CLIENT_ID=...
GOOGLE_OAUTH_CLIENT_SECRET=...
GOOGLE_OAUTH_REFRESH_TOKEN=...    # выдаст make google-auth
GOOGLE_SCAN_DRIVE=true
GOOGLE_DRIVE_FOLDER_IDS=          # пусто = весь доступный корпус
GOOGLE_MAX_DOCS=500
```

Как устроен поиск. Обход по дереву (`AncestorName`) применяется только к явно
заданным папкам: `items/root` — это лишь «Мой диск», а «Доступные мне» и общие
диски лежат вне этого поддерева и в такой обход не попадают. Поэтому по
умолчанию сервис сначала находит документы листингом Drive — он видит весь
доступный корпус — и затем запрашивает активность по каждому найденному документу.

Отсюда `GOOGLE_MAX_DOCS`: на каждый документ приходится отдельный запрос
активности, а у активного человека за квартал доступных документов бывает много.
Документы сортируются по свежести правки, и если потолок сработал, об этом прямо
написано в примечании к прогону — не «собрано всё», а «часть не просмотрена».
Сузить корпус можно через `GOOGLE_DRIVE_FOLDER_IDS`.

```bash
# APIs & Services → Credentials → OAuth client ID → тип «Desktop app»
make google-auth        # откроет браузер и напечатает готовые строки для .env
```

Помощник кладёт в вывод `GOOGLE_AUTH_MODE`, client id/secret и refresh token —
остаётся скопировать их в `.env`. Пока приложение в статусе *Testing* на consent
screen, refresh token живёт 7 дней; для постоянной работы переведите приложение
в *Internal* (если организация это позволяет) или *In production*.

Ошибки получения токена сервис объясняет текстом с конкретным шагом:
`unauthorized_client` — не настроен delegation, `invalid_grant` — токен отозван
или протух, `access_denied` — доступ сторонних приложений к Drive закрыт политикой.

## Известные ограничения

- Точное время постановки реакции в Slack API не отдаётся — используется время
  сообщения, событие помечается `meta.time_is_message_ts`.
- Идентификация актора в Drive Activity API — см. врезку выше. Практическое
  следствие: если у учётки нет прав смотреть участников документа, часть правок
  опознать не удастся и они не попадут в статистику. Это осознанный выбор в
  пользу неполноты, а не в пользу выдуманных событий.
- В режиме «только расшаренные документы» события по документам с закрытой
  лентой активности огрублены до одной последней правки (`meta.approximate`).
- Сбор коммитов идёт по репозиториям, где были push-события пользователя; коммит,
  запушенный кем-то другим, в статистику не попадёт.
- Сравнение «с прошлым периодом» считается по данным в базе: если предыдущий
  период ещё не собран, дельта будет завышена.
